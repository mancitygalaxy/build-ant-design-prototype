# 构建 Ant Design 交互原型

## 先判断入口

只选择符合当前任务的一条入口，不得默认存在旧原型。

### 从零创建

1. 读取用户给出的产品材料、页面目标、业务流程和研发约束。
2. 明确目标用户、核心任务、页面结构、关键状态和验收方式。
3. 先形成最小信息架构与关键交互链路，再开始搭页面。
4. 没有旧原型时，不虚构历史设计或迁移约束。

### 基于现有原型迭代

1. 读取原型源码与浏览器实际呈现，分别提取页面结构、视觉样式、交互状态和连续操作逻辑。
2. 保留原文件，复制出新版本后再修改，除非用户明确要求覆盖。
3. 区分“原型已有行为”“本轮新设计”“尚未确认的组件选择”。
4. 不因换技术栈而丢失已有业务契约。

## 开工前确认

从上下文和材料中补齐以下信息；只追问会改变方向的缺口：

- 最终交付：单 HTML、源码工程、可分享地址或多种形式。
- 目标设备与最小可用宽度。
- 需要做实的页面和本轮明确不做的页面。
- 是否需要对齐研发的实际依赖、目录和质量门禁。
- 关键连续操作、一次性操作、禁用条件和状态保留范围。
- 视觉基线：品牌资源来源，顶栏和侧栏尺寸，字号层级，以及默认、悬停、选中、展开等状态；即使没有旧原型，也不能直接把 Ant 默认值当成最终设计。

用户要求直接做时，使用合理假设继续，并在交付中列出假设。

## 效果优先与证据复用

保留所有必要子代理、验收维度和最终回归，只删除零新增价值的重复动作。

开始实施前，维护一份最小证据账本，记录当前状态、开放风险、证据方法、结果和结论。证据账本复用当前计划、子代理派单和验收回执，不默认新建文件，也不为记账额外运行命令。

只有验证对象与版本、风险问题、证据方法、验收口径、视口与测试状态均相同，中间没有相关修改或外部状态变化，且上次结果完整有效时，才允许复用结果。失败、截断、状态不明或能力受限的检查不得登记为已完成。

源码检查、工程构建、浏览器视觉、真实交互、独立复核和发布后回读分别验证不同风险，必须保留各自需要的证据。没有发现缺陷但关闭了预先声明的高风险项，也属于有效结果。

`Token`、工具调用、上下文压缩和子代理数量只作为复盘信号，不作为停止、换任务或减少验收的硬条件。

任务涉及多代理协作、共享状态或样式、跨模块改造、验收证据复用，或发布到可分享地址时，完整读取 [效果优先编排与证据复用](references/evidence-first-orchestration.md)。

## 组件判断

优先使用 Ant Design 的标准组件承载标准能力：

- 导航：`Layout`、`Menu`、`Breadcrumb`。
- 数据列表：`Table`、`Pagination`、`Dropdown`、`Checkbox`。
- 表单与反馈：`Form`、`Input`、`Select`、`DatePicker`、`Modal`、`Alert`、`Message`。
- 状态切换：`Radio.Group`、`Segmented`、`Tabs`。

当业务形态无法由单个标准组件准确表达时，创建“业务复合组件”，内部仍使用 Ant 的交互原语。例如：多种触发方式会联动配置区、输入区、按钮、影响说明和连续运行态时，不直接套默认 `Tabs` 或 `Segmented`，而应使用受控 `Radio.Group` 加自定义卡片呈现。

如果具体选哪个 Ant 组件会明显改变交互或呈现，必须在实施该处前问用户。说明 2—3 个候选组件及各自影响，不替用户猜。

### 标准组件与默认样式分开判断

使用 Ant 标准组件，代表复用其语义、交互和可访问性，不代表接受其默认尺寸和视觉。

- 对 `Layout`、`Menu` 等框架组件，先核对显式 props、`ConfigProvider` 或组件 token、局部 CSS 和浏览器 computed style，再判断问题来自组件限制还是实现未覆盖。
- 顶栏与侧栏尺寸、菜单默认态、悬停态、选中态、子菜单背景、字体、图标和间距应依据本次视觉基线显式设置，不得让未经确认的默认 token 混入最终交付。
- 仅在已确认拥有使用与交付权限时复用 Logo、自绘 SVG、品牌字体或其他品牌资产；通用 Ant 图标只能作为临时方案，不能在未确认时视为视觉对齐完成。
- 组件 token 优先局部作用于目标组件，避免同时改变账号下拉菜单等其他同类组件；响应式规则不得反向覆盖已经确认的壳层尺寸。

### 高频列表、筛选与表单的实施门禁

- `Table` 实现前先定义每列的宽度、折行、截断、条件式 `Tooltip`、固定和滚动策略，并用真实长度数据与最小可用宽度验收。固定列的背景、悬停和分隔投影要连续；没有被遮挡内容时不应常驻投影。
- `Tooltip` 用来补充被截断的信息时，只在文本实际溢出后出现；完整显示的内容不重复提示。帮助说明类 `Tooltip` 另按业务需要判断。
- 轻量、可撤销、无需等待的本地筛选优先即时生效，并同步更新列表、已选数量和分页；多条件组合、远端请求或高成本查询才保留“应用”步骤。
- 同一业务对象的新建与编辑优先复用一份表单结构和校验规则，由业务契约决定字段可编辑性。编辑态保留不可改字段的原值和可见性，提交时只更新允许修改的字段。
- 复制、展开、切换等结果已在当前控件附近可见的操作优先使用局部反馈；保存、失败、危险操作和不可见异步结果再使用全局消息，不重复播报用户已经看见的结果。
- 弹窗标题下的辅助文案只有在补充影响范围、前置条件、风险或恢复方式时保留；仅复述标题或实现背景的小字不作为固定模板。

## 工程策略

用户提供研发工程或技术栈时，以真实依赖和源码为准，不根据截图文字或方案说明假定已经实现。

在没有其他约束时，优先使用：

- React + TypeScript + Vite。
- Ant Design 6 与 `@ant-design/icons`。
- pnpm 锁定依赖。
- SCSS 管理全局样式和独立组件样式。
- `oxlint` 与 TypeScript 检查作为基础门禁。

只有出现两个及以上真实页面、需要地址直达或刷新恢复时，再接入 React Router 和 Hash 路由。不要为尚未迁移的空页面提前堆路由。

需要本地交付单文件时，可使用 `vite-plugin-singlefile`。它是交付层能力，不代表偏离研发的 React / Ant 技术路线。

## 状态与连续交互

先写状态契约，再写界面：

- 运行态按业务实体或交互会话的稳定 ID 隔离，避免不同实体共用一套全局状态。
- 切换展示模式不能重置草稿、虚拟时间、消息或执行记录。
- 一次性事件和可重复输入必须使用不同的判定字段。
- 对长任务期间的追加输入，预先定义合并、中断、重启和结果替换规则，并通过连续输入验收。
- 如果跨实体切换会导致运行态歧义，阻止切换并解释原因，不要静默丢状态。
- 禁用动作必须同时展示原因和恢复方式。

### 跨模块数据契约

当资产管理、创建流程、列表和工作台共享业务对象时，先定义引用与冻结边界：

- 为共享业务对象分配稳定 ID；使用 ID 建立引用，名称只用于展示，只有兼容旧数据时才按名称回退。
- 明确哪些数据在创建时冻结，哪些数据在运行时实时读取；恢复历史状态时使用已经约定的来源，不能被后续编辑静默改写。
- 按业务实体和资产类型分别记录一次性结果；不要使用名称或单个通用布尔值代替各类业务规则。
- 只在初始化或显式迁移时对旧数据做一次性回填；不得在每次渲染、进入页面或保存时重复补全并覆盖旧数据。
- 删除共享资产前按稳定 ID 检查全部引用方；仍被引用时阻止删除，并说明引用位置和可恢复路径。
- 分别验收历史数据和新建数据：历史数据保持原有展示与状态，新建数据使用最新配置形成独立状态，后续资产变化遵守已经定义的冻结或实时读取边界。

## 协作与并行

子代理数量由独立风险问题决定。存在可并行的独立风险时，优先安排源码基线、浏览器基线、状态契约、视觉验收、交互回归、工程构建和交付检查。

- 每个子代理必须说明风险问题、独有证据、决策影响和停止条件，不能笼统地重复“全面检查一下”。
- 不同文件或组件边界明确时可以并行实施；同一文件、共享状态核心或全局样式同一时间只设置一个写入所有者。
- 同一模块可以由多个代理复核，但必须负责不同风险格、使用不同证据方法，或承担明确的对抗性独立复核。
- 验收代理可以在实施期间并行准备测试数据、页面状态和检查路径。
- 实施者自测不能替代高风险独立复核；简单局部任务可以合并角色，但不能省略与风险相对应的证据维度。
- 子代理只返回新增事实、缺陷、排除证据和具体来源；主代理核验关键结论，不重新完整执行其全部过程。

## 实施顺序

1. 盘点材料、源码、当前浏览器状态和不可修改的原件。
2. 固定本轮范围、当前状态和验收清单，建立改动与风险的对应关系。
3. 建立或复用源码工程，核对并锁定真实依赖。
4. 先做应用框架和主任务流，再按独立业务闭环拆分复杂区域。
5. 每完成一个业务闭环，根据实际改动执行风险匹配的定向构建与定向验收；已有证据只有满足复用条件时才可沿用。
6. 共享主题、壳层、状态模型、数据契约或构建配置发生变化时，主动扩大回归范围。
7. 修复问题后，先重新执行受影响的定向检查；没有受影响的有效证据继续沿用。
8. 生成最终交付文件，核对其来自最新源码，并冻结最终候选版本。
9. 对最终候选版本执行本轮验收清单的完整回归；过程中已通过的定向验收不能替代这一步。

## 浏览器验收

本地 HTML 或静态原型必须通过仅绑定 `127.0.0.1` 的 HTTP 服务打开，不使用 `file://` 作为验收依据。

### 定向验收

每次实质修改后，根据改动可能影响的风险执行定向验收：

- 局部文案、颜色或间距：检查目标区域和关联状态。
- 局部组件样式：检查默认、悬停、选中、禁用和目标宽度。
- 全局主题 `token`、`Layout` 或 `Menu`：检查全部壳层状态和相邻区域。
- 状态处理或数据模型：检查相关状态转换、保存、切换、失败和恢复。
- 构建配置、依赖或单文件插件：重新执行完整工程与交付门禁。

源码、配置、依赖和相关页面状态均未变化时，不机械重复相同构建或相同页面状态检查。

### 最终候选验收

至少检查：

- 页面成功加载，关键区域没有溢出、竖排、遮挡或双重滚动。
- 关键按钮、筛选、弹窗、列表进入和返回路径可用。
- 模式切换同步更新配置、摘要、输入状态、按钮和影响说明。
- 草稿、实体状态和一次性动作限制按状态契约保留。
- 连续输入遵守已定义的合并、中断与重算契约。
- 类型检查、lint 和生产构建通过。
- 单 HTML 交付没有外链脚本和外链样式。
- 能读取控制台时检查页面错误；能力受限时明确区分源码检查和浏览器交互验收。
- 对顶栏、侧栏和菜单读取浏览器 computed style，至少核对宽高、背景、文字色、字号、字重、间距、圆角和图标尺寸；悬停、选中和子菜单展开态必须实际触发后分别检查。
- 壳层组件还要分别验收侧栏收起态、下拉打开态和相邻区域的指针切换：收起时核对图标中心与侧栏中心，下拉打开后核对菜单项、禁用状态和点击反馈，横向扫过顶栏相邻区域时检查边框、阴影和过渡是否出现瞬时闪线。键盘的 `focus-visible` 轮廓属于可访问性反馈，应与悬停异常分开判断。
- Ant `Menu` 的子菜单开合要同时核对状态和实际可见性：检查 `aria-expanded`、隐藏类和 computed style 是否一致。自定义布局不得覆盖组件的隐藏样式；侧栏整体展开或收起时如有选中项闪烁，要定位仍在离场的旧节点或具体过渡属性，保留正常动效，只隔离本不应显示的状态。除非用户明确不要该动效，不得用关闭整组 motion 代替修复。
- 高密度列表还要验收长字段折行或截断、条件式 `Tooltip`、分组箭头、横向与纵向滚动、分页联动、固定操作列投影和整行悬停连续性；新建与编辑弹窗要分别核对字段位置、权限和提交结果。

连续迭代期间，临时服务仍然健康、指向当前交付目录且页面可以刷新到最新构建时，复用现有服务和浏览器页。任务验收完成后再关闭本轮临时服务和临时页面，不关闭用户原有页面。

## 最终回归、交付与发布回读

最终回归分别确认工程构建、浏览器视觉、关键交互、状态契约和交付文件来源。不同维度可以并行执行，但必须汇总到同一个最终候选版本。

最终说明：

- 新文件与源码工程位置。
- 本轮已完成、尚未迁移和刻意保留的范围。
- 实际通过的构建与浏览器验收项。
- 与研发技术栈一致和暂未对齐的部分。
- 一份按页面框架、列表、弹窗、工作台、复杂组件、状态链路和证据区排列的逐项过稿清单。

用户要求发布或提供可分享地址时：

1. 发布前取得明确授权。
2. 只发布已经通过最终回归的候选版本。
3. 使用目标平台对应的正式工作流完成发布。
4. 发布后从远端重新打开，核对版本、页面加载、关键入口和至少一条主链路。
5. 记录远端目标、发布版本和回读结果。

本地验收不能替代发布后回读。
