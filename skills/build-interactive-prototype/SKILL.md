# 制作与修改交互原型

交付能实际操作、符合本轮需求、便于继续修改的原型。适用于 HTML、React、Vue、Ant Design、Fusion 等已有方案；技术选择服务于项目。面向用户说明做了什么、效果如何和还有哪些限制，必要的代码与配置名称保留原文。

## 判断任务和技术方案

- 新建原型：先确定用途、主要任务和交付形式。用户已有技术要求时按要求执行；没有指定组件库时，集中问一次“这次是否采用 Ant Design？”。回答前可整理需求与材料，先不选定技术方案。
- 已有工程：沿用实际组件库、依赖、目录和构建方式，包括 Fusion 或独立 HTML。已有方案清楚时直接继续，不再询问是否换成 Ant Design。
- 明确采用 Ant Design 时，读取 [Ant Design 制作分支](references/ant-design.md)。其他方案使用项目现有组件和规范，不套用 Ant Design 模板。
- 只要求评审、列差异或检查问题时保持只读；使用适合的评审流程。要求检查并修复时，按已经授权的范围实施。
- 按飞书反馈修改时，配合 `iterate-prototype-from-feishu-feedback`：它负责读取反馈、整理本轮条目与回写状态，本 Skill 负责实现及验收。只读反馈不启动修改。
- 同一任务经过反馈、评审、对版和修改时，沿用同一份问题清单、来源定位与条目编号；新增发现补进原清单，不为切换 Skill 重建需求或另开一轮完整审计。只加载当前阶段需要的说明，已经明确的范围、目标和授权继续沿用。
- 正式生产系统的接口、鉴权、数据库迁移和部署按项目规则及授权处理，不因制作原型而扩大改动范围。用户明确要求重新设计或迁移技术时，重新确定变化与验收范围。

## 开始前恢复项目情况

先读真实项目的规则、交接卡、需求、源码和现有检查；项目已有原型方法文档时一并读取，不要求固定文件名。已有页面同时检查实际浏览器行为，截图不能证明取消、重开或保存规则。

从上下文补齐以下信息，只集中追问会改变方向、范围或验收的缺口：

- 谁使用、完成什么任务，本轮制作哪些页面，保留哪些行为。
- 交付源码、单 HTML 或完整网页目录，是否明确要求发布。
- 目标设备、最小可用宽度、品牌、视觉参考与当前页面版本。
- 关键操作、异常恢复，以及切换、刷新、返回和取消后的状态。
- 使用演示数据还是真实接口，哪些能力需要做实，典型数据规模是多少。

工程细节由执行者根据材料判断。已经明确的决定不重复询问；必要来源或授权不足时暂停依赖它的步骤，说明缺口，继续不依赖该来源的工作。

需求尚在共创时，先给出对用户任务的理解、推荐方案及主要取舍，只询问会改变产品方向、范围或验收的决定。明确部分继续推进；新决定更新原条目的目标与通过条件，替换失效方案，不把探索中的想法写成已确认需求。

## 按场景选择做法

| 本轮任务 | 处理方式 |
|---|---|
| 从零制作 | 先梳理页面层级、主任务和关键状态，再实现界面；使用模板时替换产品名称、页面、数据和检查场景 |
| 修改已有原型 | 保存可恢复的改前版本，明确本轮变化，复用稳定实现；读 [沿用已有原型](references/existing-project.md) |
| 基于旧版适配新业务 | 区分原版沿用能力、已确认差异和待决定规则；读 [复用与业务适配](references/existing-project.md)，同时检查旧入口和新入口 |
| 页面和功能不变，只优化代码 | 保存改前参考，读 [代码整理与前后对比](references/behavior-preserving-refactor.md)，分别证明内部改善与外部行为保持约定 |

沿用项目 Git 主线和恢复机制；无版本管理或用户明确要求副本时才复制目录。保护无关修改和用户数据，不为套用模板重写稳定工程。从构建产物反查维护源码；直接编辑生成文件的条件见已有原型说明。

同时包含预期可见变化和纯代码优化时，先完成可见变化并验证，再保存该版本作为代码优化的比较依据。

## 页面、数据和状态

- 先让主任务、信息层级和主要按钮清楚，再完善次要内容。优先沿用已确认的品牌与布局。新建视觉方向、视觉改版或按参考图制作时，读 [视觉参考与效果检查](references/visual-design.md)，按需使用其中的参考库索引；普通局部修改沿用既有方向，不逐个确认组件默认值。
- 按操作含义选控件。同一用途的标题、尺寸、字号、边框和状态保持一致；差异有业务依据。涉及表格、筛选、菜单、表单、弹层或异步取数时，按需读 [组件制作与页面检查](references/component-checks.md)。
- 用正常、空白、长文本和错误数据检查页面。分别核对业务为空、样本未采集、加载中、请求失败和模拟结果，不能互相代替；零值、缺失、无权限、待配置仍按业务定义区分。主任务所需的列表、详情与附属资料要能连贯演示，合成边界数据与用户真实数据隔离。
- 完整走通进入、输入、提交、结果、返回及必要的失败恢复。不能只证明按钮能点击；复制、导出要核对实际内容。
- 明确业务数据由哪个模块保存和更新。对象使用稳定 ID；共享数据明确唯一来源，区分实时引用与创建时保存的副本。
- 切换、刷新、取消后保留或重置什么，以产品约定为准。没有重置要求时保留草稿和结果；可能丢数据时按约定保留、提示或拦截。
- 分别处理一次性动作、重复提交与异步任务，防止重复执行、旧结果覆盖新输入和不同对象串数据。检查保存失败、重试及旧数据恢复。
- 删除前检查引用，旧数据只在约定时机迁移。多轮对话或历史记录至少检查两轮，确认旧轮次可定位且未被覆盖。
- 关键表单和弹层检查键盘操作、可见焦点、字段说明、错误提示及关闭后的焦点去向；目标宽度、对比度和窄屏可读性一并检查。
- 反馈优先靠近操作；保存、失败和不可见异步结果需要清楚提示。演示数据明确标注，不捏造真实接口、MCP 调用、模型内部过程、费用或外部执行结果。

包含 Agent 测试对话、资产库或冻结快照时，读 [工作台案例](references/agent-workbench-example.md)。连续输入是否归入同一个 `Request`，由当前业务约定决定。

## 检查到什么程度

按 [质量与性能规则](references/prototype-quality.md)选择本轮范围，复用项目已有检查。局部文案和样式检查相关区域与状态；数据、保存、共享布局或构建变化时扩大到受影响路径，按实际风险测量性能。纯代码优化同时核对改善依据与行为保持。没有对应脚本时用等价检查；需要构建的工程检查构建，直接维护的静态文件核对实际交付内容。

本地页面通过仅绑定 `127.0.0.1` 的 HTTP 服务检查，按实际反馈触发点击、输入、展开、切换、刷新等动作。尺寸和对齐问题读取元素与计算样式，检查相关控制台错误或警告。

只重做受影响、失效或不完整的检查。同一次任务涉及多个 Skill 时共用检查结果；最终交付前确认结果仍覆盖当前版本。相关检查失败、条件不足或不可比较时，明确列为未完成。

本轮引入的问题直接修复；旧问题保留依据和后续建议。不通过缩小样本、删除功能、覆盖旧参考或放宽标准让检查通过。大规模架构、业务或保存规则变化超出当前范围时先讨论。

## 按需使用工程和检查资料

- 已确认使用附带 React / Ant Design 模板，或需要了解其目录、初始化和交付机制：读 [代码组织与模板使用](references/quality-first-engineering.md)。这些目录和工具要求只用于该模板，不强制其他工程采用。
- 需要测量加载、请求、筛选或数据规模：读共同质量规则；使用附带执行器时再读 [性能配置与执行](references/performance-checks.md)。首次记录不等于达标。
- 使用附带浏览器脚本、建立参考或排查截图差异：读 [浏览器检查与截图对比](references/browser-checks.md)。登记场景之外的操作仍需实际验证。
- 跨模块变化、复杂分工或汇总多份结果：读 [协作与检查结果复用](references/evidence-first-orchestration.md)。是否使用子代理服从工具能力和当前授权，不因 Skill 自动要求分工。

本包的模板和脚本完整保留，可在适合的工程中采用；优先使用项目已有的等价检查，不为了使用工具更换技术栈。

## 完成与交付

实施过程中检查每项改动关联的页面、操作和代码；共享布局、数据或构建变化时扩大范围。最终核对交付来自当前维护源码，必要检查完整，用户数据与配置得到保留，剩余限制有明确说明。

- 单 HTML 核对构建结果与交付内容一致，符合资源内联和外链约定；网页目录核对完整资源、入口与路由引用。
- 已确认使用附带模板时，完成初始化与检查参考后运行一次 `pnpm run deliver`；它包含完整检查，不连续重复 `verify:release`。已有工程沿用原交付入口。
- 复用健康的预览服务。结束后关闭本轮验收临时资源；保留用户仍需访问的交付服务及原有页面，并说明启动方式。重新访问失败时核对服务、接口与页面版本。
- 反查本轮最终可见差异是否都有需求或必要适配依据；涉及反馈、截图或 PRD 时，核对其是否仍对应交付版本。按已有授权更新受影响部分，未覆盖的资料更新明确列出。
- 简要说明完成范围、交付位置、页面与操作检查、相关性能结果、保留的业务差异和未完成项。没有剩余决策时直接交付。
- 反馈或评审修复按原条目返回本轮变化、实际交付版本、验收动作与结果、证据位置和剩余问题；分清已修复、复验未通过、受阻或经检查无需改动。反馈流程据此决定哪些原记录可以回写，不把建议已采纳、代码已改或构建成功直接当成整条验收通过，无需重复生成报告。

发布、回推或对外发送需要具体目标和范围的明确授权；已有授权不重复询问。使用项目正式入口，只发布已检查版本，远端重新核对版本、加载、关键入口和至少一条主任务。分别报告本地交付、状态回写和远端发布结果。
