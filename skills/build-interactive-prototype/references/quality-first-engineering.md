# 代码组织与模板使用

用于从零制作或长期维护 React / Ant Design 原型。目标是从开始就保持代码职责清楚、改动可以验证、文件能够可靠交付。

各类任务的共同质量要求见[共同规则](prototype-quality.md)，性能测量见[性能配置](performance-checks.md)，浏览器执行细节见[浏览器检查](browser-checks.md)。

## 何时使用模板

确认采用 Ant Design 后，从零制作、只有零散 HTML 且本轮需要建立工程，或目录尚未稳定时，优先使用 `assets/react-ant-prototype-starter/`。

先替换产品名、页面、数据和检查场景。用户已提供真实研发工程时，保留原依赖、目录和构建方式，逐步补充本轮必要检查。

## 代码放在哪里

```text
src/
├── app/          # 页面框架、路由、跨页协调
├── pages/        # 页面数据及状态管理
├── features/     # 可以独立完成一项任务的业务模块
├── components/   # 接收业务数据、负责展示的组件
├── domain/       # 类型、纯函数、业务规则
├── data/         # 演示数据和数据转换
└── styles/       # 确有需要时建立的共用样式
```

依赖关系保持清楚：

- `app` 组合页面，不堆具体表格、弹窗和业务表单。
- `pages` 使用业务模块、展示组件、业务规则和数据；页面之间不相互导入。
- `features` 使用展示组件与业务规则，不反向依赖页面。
- `components` 通过属性接收业务输入，不导入页面、应用框架或业务模块。
- `domain` 不依赖 React、Ant Design、页面或浏览器存储。
- `data` 不依赖页面框架、页面、展示组件或业务模块。

展示组件可以管理展开、悬停和文字溢出等临时视觉状态。业务数据、跨模块协调与保存由明确模块负责；不只凭出现 `useState` 或 `useEffect` 判断违规。展示组件不直接读写浏览器存储。

## 先写清状态规则和检查步骤

写界面前明确两件事，复用现有文件，不重复建文档：

1. 数据如何管理：对象 ID、负责模块、默认值、保存位置、恢复时机、一次性限制、异步顺序和旧数据兼容。
2. 如何检查：真实路由、关键状态、用户动作、预期结果、失败恢复和本轮范围。

`prototype.acceptance.json` 保存可执行的验收约定。每增加一个真实页面或关键流程，同次修改补充相应路由、状态与操作，并用 `browserScenarioId` 关联 `prototype.browser.json` 的场景。缺少关联或存在无人引用的场景时，检查失败。

操作步骤至少表达“初始状态 → 用户动作 → 中间反馈或限制 → 最终结果 → 刷新或返回后的状态”，不能只写“按钮可点”。

## 处理超大文件与样式问题

`prototype-architecture.json` 和 `pnpm run check:architecture` 负责结构检查。默认行数如下，达到预警时分析职责，不机械拆文件：

| 文件类型 | 预警 | 阻止继续增长 |
|---|---:|---:|
| 页面框架 | 600 行 | 900 行 |
| 管理页面状态的模块 | 800 行 | 1200 行 |
| 展示组件 | 300 行 | 500 行 |
| 业务模块 | 600 行 | 900 行 |
| 样式文件 | 800 行 | 1200 行 |

达到上限后不能继续堆代码。优先抽取纯函数、配置、字段定义、受控展示区域或独立业务任务；拆分涉及状态归属或执行顺序变化时先明确风险。大规模调整先讨论，局部且可验证的改进直接完成。

接入旧工程时可一次性记录经过核对的现有超限问题，后续只能保持或降低；新增文件按默认规则执行。不得提高上限、重建旧问题记录或新增例外来放行本轮问题。

样式默认不新增 `!important`，直接覆盖 `.ant-*` 的选择器会收到提示。优先使用 `ConfigProvider`、组件 token 或有明确容器边界的局部样式；确有必要的覆盖要说明原因。已存在的数量只作为不得增长的参考。

改动涉及结构或样式时，按相同方法检查前后行数与覆盖数量。行数减少只是线索，还需证明职责、重复逻辑或依赖确有改善。

## 原始数据与脱敏数据

同时维护两种数据时，共用组件、状态、路由、业务函数、操作场景和构建方式，只区分数据入口：

```text
data/
├── schema.ts
├── original.ts
├── sanitized.ts
└── index.ts
```

两套数据满足相同类型和稳定 ID 规则；不复制整套页面分别维护，也不在构建后直接替换 HTML 文本。两版分别保留截图和交付哈希，脱敏版构建前后检查敏感信息。

## 改动后检查什么

文案、演示数据或局部展示检查相关页面和操作；状态、存储、异步顺序变化增加保存与恢复检查；全局框架、路由、依赖变化覆盖全部受影响页面及主任务。纯代码整理保留改前参考，证明页面和行为没有变化。

首次引入或修改对比机制时，先检查正常页面并保存参考，再在可丢弃的样例中制造文案、样式或操作错误，确认能识别，撤销后对同一参考通过。已有执行器版本相同且相关测试有效时可复用结果。不能用故障结果或重构后的结果覆盖改前参考。

## 构建和交付保持一致

构建清单记录源码指纹及完整资源清单；性能配置与交付方式一并识别。`verify:delivery` 检查源码与构建是否一致、资源是否缺失或被改写，以及入口引用是否有效。

- `deliveryMode` 省略或为 `single-html` 时，将 `dist/index.html` 交付为 `deliveryFile`，不依赖分离脚本和样式。
- `deliveryMode: web` 时按 `deliveryDirectory` 交付完整目录，允许拆分资源，复制后逐文件核对。
- 交付脚本不拼接或修改产物；已有交付按模板规则保留可恢复版本。
- 敏感信息扫描覆盖源码、配置、测试参考、`dist/` 和 `delivery/`，最终文件生成后再扫一次。

持续集成复用 `pnpm run verify:release`。接入 GitLab 前核对 Runner、镜像、Node、pnpm、浏览器和网络；可以适配运行环境，不删掉必要检查。新环境单独建立经过检查的浏览器和性能参考，不能直接采用其他系统的记录。

## 接入旧工程

先保存源码、锁文件、交付物和关键页面参考，再只读检查现有结构。审核已有超限问题，先保证本轮不再增加，再随相关功能修改逐步改善。补充本轮需要的来源核对和自动检查，不为统一目录重写稳定模块。

## 模板初始化和执行顺序

1. 替换示例页面、数据、稳定 ID、存储键、验收约定、浏览器场景和性能配置。
2. 在 `prototype.project.json` 填写项目标识、交付方式及文件名或目录名。全部示例已替换后才设 `initialized: true`；不能删检查或提前改标记绕过。
3. 运行 `pnpm run build`，按需求检查页面，再用 `pnpm run baseline:browser` 保存首份参考。必要时完成前述故障识别与恢复验证。
4. 运行 `pnpm run baseline:performance` 记录首次性能结果；记录成功不等于性能达标。
5. 交付运行一次 `pnpm run deliver`，其中已包含结构、验收约定、类型、代码、构建来源、浏览器、性能和敏感信息检查。只检查不复制时用 `verify:release`，不连续重复两套完整入口。
6. 实际需要持续集成时再接入模板的 `.gitlab-ci.yml`。开发中只检查受影响范围。

安装和运行前核对 `packageManager`，外层及嵌套命令使用相同 pnpm 版本。存在多个入口时优先用项目指定入口，不为单个项目修改全局配置。

新浏览器配置支持环境设置、悬停、键盘与焦点检查；旧结果需按[浏览器说明](browser-checks.md)核对后补环境记录。保持严格像素比较，不以更新参考掩盖失败。真实原型仍需登记主成功流程、关键限制、保存恢复和必要的失败恢复。
