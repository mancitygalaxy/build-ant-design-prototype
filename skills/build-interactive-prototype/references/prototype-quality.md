# 原型技术质量与性能

本文件是制作与迭代的共同完成条件。用户只说“做原型”“继续改功能”时也执行，不等待额外的优化口令。安装包内此文件由维护仓库的 `shared/prototype-quality.md` 生成；维护时只改主源。

## 按影响选择检查

开工时明确本轮行为约定、状态所有者、数据规模、风险与可复用证据，复用项目已有契约和检查，不为填表新建重复文档。

| 改动 | 必要范围 |
|---|---|
| 文案、间距等局部修改 | 目标区域、相关状态和操作；无相关风险时不启动全项目重构或无关性能测量 |
| 取数、列表、筛选、保存、状态或数据规模 | 相关代码边界、结果一致性、请求与计算、操作耗时、刷新及保存恢复 |
| 首次交付、跨模块整合、构建方式变化 | 关键链路、当前与较大规模、生产构建、最终交付物完整性 |
| 界面和功能不变的技术优化 | 先冻结改前基线，再分别证明内部改善和界面、业务结果、状态、保存行为保持约定 |

先读项目交接卡、源码和现有检查。沿用项目 Git 主线、分支或 worktree 及恢复方式；无版本管理或用户明确要求副本时才复制完整目录。不得复制旧目录后另立维护主线。

有效证据可按版本、受影响范围、数据、环境和验收口径复用。最终交付前检查证据是否仍覆盖最终候选；无关代码变化不要求重跑完整检查。必要证据失败、缺失或受阻时明确未完成，不能报告通过。

## 开发时承担质量责任

- 状态按职责归属：业务状态、异步任务、跨页共享与持久化由明确的所有者管理；展开、悬停、测量溢出等纯视觉状态允许在组件内部封装。
- 优先复用已有模块，收敛重复逻辑、重复请求和大数据复制；业务规则用可验证的纯函数或边界清晰的模块承载。文件变短只是结构信号，不能单独证明可维护性改善。
- 行数用于结构预警；项目已有阻断线继续遵守，但不能机械拆文件、转移复杂度或凭行数宣称优化完成。
- 本轮引入的明显质量或性能退步必须修复。已有问题记录改前证据、影响与后续建议，不要求本轮清零，也不能把新增问题登记成历史债务。
- 局部、可验证、保持约定行为的优化直接实施，包括减少重复计算、请求去重、清晰的状态归属和按实际数据需求加载。缓存必须验证失效、刷新、新旧输入和保存后的一致性。
- 大规模架构调整、技术栈迁移、业务规则、可见反馈或保存语义变化先讨论。不能通过减少功能、缩小数据集、隐藏慢路径或修改基线让优化“通过”。

纯技术优化要有明确收益证据，例如消除一处重复规则、减少跨层依赖或同条件实测改善；同时保留文本、视觉、交互、数据结果、存储及恢复证据。速度提高不能替代正确性回归，截图相同不能替代状态回归。

## 性能条件在开工时登记

对需要测量的场景，先登记以下最小条件，优先使用现有配置：

- 场景与用户操作，测量起点，以及主要数据和操作真正可用的完成条件；页面框架出现或网络空闲不能单独当作完成。
- 样本来源、固定版本或内容哈希、数据条数及规模；覆盖当前规模与较大规模。
- 浏览器版本、视口、运行环境、生产构建版本。浏览器首次访问与服务端首次读取分别标记；服务端缓存未知就写未知，不能合称“冷启动”。
- 首次打开、重复访问、切条件、搜索等本轮相关路径；耗时、请求数量、传输量和构建资源体积预算。必要时补接口耗时、渲染或重复计算证据。
- 项目体验目标与允许的必要增长。新功能确需增量时，实施前记录原因和预算，保留原记录。

本 Skill 包不要求其他 Skill 已安装。使用既有工程时可用等价检查；使用附带构建模板时，按它的性能配置和执行器登记，不强制旧工程迁移模板。

## 比较与结果判定

耗时默认采集五次，以中位数比较同条件基线。超过旧值 20% 且至少增加 100 毫秒时，独立复测一轮；两轮都超出才判为新增退步。这是可调整的防抖边界，不是所有原型的体验目标。独立复测必须重新执行场景，不复制第一次结果。

请求数量、传输量和资源体积按场景预算判断。历史超预算项只有在改前已登记证据和不增长上限时才能作为旧问题保留；新增超预算仍须处理。

新场景没有旧基线时，先建立首份记录，并单独验证已登记目标；“基线已记录”不等于“性能达标”。缺目标、缺必要样本、浏览器不可用、完成条件失效或前后输入不一致，都应标记受阻或不可比较，不能误报通过。

优化任务不得自动重写基线。环境或样本需要变更时，保留旧记录，明确变更原因，分别建立同条件证据后再比较。结果中区分：本轮通过、已登记历史问题、未完成项。

## 完成交付

交付前自动完成本轮必要的检查、测量、局部优化和复验，再核对最终产物来自已验收的源码。结论用最少信息说明改了什么、改善证据、行为保持证据和剩余限制。反馈表只把相关质量与性能检查也通过的条目标记完成；只读审计不实施优化。
