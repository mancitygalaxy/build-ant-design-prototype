# 只整理原型代码，不改变页面和功能

用户只需要说“整理一下代码，页面和功能别变”。执行时用本文件把这句话展开成具体检查项：保持用户看到和操作到的结果不变，同时证明代码确实变得更容易维护、复用或构建。

## 一、确认适用边界

同时满足以下条件后再开始：

1. 存在可维护源码，且能够从源码稳定生成当前交付物。
2. 当前版本可以实际运行，并能覆盖用户要求保持不变的页面与状态。
3. 用户明确不改功能、信息、文案、视觉、交互、路由和状态与保存规则。
4. 内部优化目标可验证，例如减少重复实现、缩小超大模块、降低复杂度、减少无用包体、改善运行指标或增强构建可靠性。

遇到以下情况时退出本模式：

- 本轮允许改变页面呈现、交互结果或业务规则。
- 需要新增功能、修改文案、调整布局、改变默认值或反馈方式。
- 只有压缩后的交付 HTML，且无法可靠恢复维护源码。
- UI 框架、依赖大版本或状态架构迁移尚未证明能够保持等价。
- 需要超出已授权原型工程的生产接口、鉴权、数据库或正式运行时改造；原有服务可在授权范围内诊断与局部优化，但必须验证数据和保存语义。

混合任务必须分两阶段执行：先按普通迭代完成预期可见变化并保存新的改前版本，再开始整理代码。不得在同一次修改中混入“预期变化”和“意外回归”。

## 二、记下哪些内容必须保持不变

把“页面和功能别变”展开成可核对的清单。

### 页面内容

- 页面、页签、字段、按钮和弹窗名称。
- 字段顺序、可见条件、默认值和数据排序。
- `placeholder`、辅助说明、空态、校验、错误和结果反馈。
- 截断、折行、`Tooltip`、展开内容和复制结果。

### 页面样式

- 页面结构、元素顺序、布局、尺寸、间距和响应式边界。
- 字号、字重、颜色、边框、圆角、阴影和图标。
- 默认、悬停、聚焦、选中、展开、禁用、加载和错误状态。
- 滚动、固定列、弹层位置、遮罩和层级关系。

### 操作与状态

- 路由直达、刷新、前进、后退、重定向和离开拦截。
- 点击、输入、筛选、分页、切换、保存、取消、删除和复制。
- 重复执行、一次性限制、运行中禁用、失败恢复和旧数据恢复。
- 管理状态的模块、稳定 ID、本地存储结构、改前快照和数据引用关系。
- `timer`、异步回调、事件顺序和滚动位置。

### 交付方式

- 交付文件类型、目标位置和来源源码。
- 单 HTML、资源内联、外链限制和正式路由集合。
- 构建环境、依赖锁定方式和必要质量检查。

“保持不变”指用户看到和操作到的结果相同，不要求源码、构建产物、页面结构 `DOM` 或交付文件的字节完全相同。只有页面结构会影响样式、交互结果或自动化检查时，才把对应结构列入检查范围。

## 三、保存改前版本

修改源码前完成以下动作：

1. 记录改前交付物、维护源码、输入文件清单、版本标识和哈希。
2. 运行现有代码检查（lint）、类型检查、状态测试、生产构建和交付验证。
3. 通过只绑定 `127.0.0.1` 的 HTTP 服务打开改前版本。
4. 按场景固定浏览器版本、语言、时区、字体、设备像素比 `DPR`、页面宽高、数据和存储；涉及日期的场景再固定当前时间。模板配置与旧参考采用见[浏览器检查](browser-checks.md)。
5. 为相关路由建立“页面 × 视口 × 关键状态 × 关键动作”矩阵。
6. 保存页面文本与字段顺序、浏览器计算后的关键样式 `computed style`、截图、控制台记录和交互结果。
7. 提前明确动态区域如何固定。模板按解码后的像素严格比较；其他既有工具若需区分抗锯齿噪声，应在改前确定判断方法并保留依据。

改前版本和改后版本必须使用同一环境与同一输入。不得在差异出现后才新增屏蔽区域、扩大容差或更新改前记录。

新增自动对比工具时，先在可丢弃的测试版本中制造一次文案、样式和操作差异，确认工具能够捕获，再撤销该差异。工具只能降低漏检概率，不能替代真实操作验收。

## 四、优先做哪些改动

优先处理：

- 抽取函数体不变的纯函数、静态配置、类型和格式化逻辑。
- 抽取不新增 DOM 包裹、不改变元素顺序的受控展示组件。
- 合并重复实现，统一共享样式和数据入口。
- 改善类型约束，但不新增运行时分支或默认值。
- 强化构建、生成数据检查、交付目标保护和写后校验。
- 删除能够证明未被读取的代码或数据。
- 优化能够用相同输入复测的包体、渲染或查找性能。

以下改动默认高风险，必须独立执行并扩大回归：

- 改变管理状态的模块，移动 `effect`、`ref`、`timer`，或调整异步执行顺序。
- 改变事件绑定位置、元素 `key` 或操作顺序。
- 更换组件、废弃属性、依赖版本或路由实现。
- 引入 Context、状态管理库、Reducer 或新的缓存机制。
- 改变稳定 ID、本地存储结构、数据生成顺序或旧数据迁移逻辑。
- 合并或重排可能改变 CSS 层叠顺序的样式。

不要因为文件很长就直接拆分。先看状态由谁管理、哪些逻辑可以独立，以及展示组件的职责，再决定改动。

## 五、一次只改一小块

每整理一小块代码，都执行：

1. 写清内部优化目标、允许修改的边界和可能影响的结果。
2. 记录开工前指标，例如重复规则、依赖关系、同输入计算量、文件体积或构建风险点；文件行数仅作辅助信号。
3. 一次只修改一个结构边界，不顺手清理其他问题。
4. 运行受影响的 lint、类型、状态测试、构建和交付检查。
5. 对改前版本和改后版本执行同输入、同状态的定向浏览器对比。
6. 核对本次内部指标是否实际改善。
7. 发现任何未声明差异时，修复或撤销当前变更；不得用改后结果覆盖改前记录。

共享主题、页面框架、状态模型、数据约定、构建配置或复杂运行逻辑发生变化时，检查全部相关页面、宽度和操作状态。高风险变更保留独立复核；实施者自测不能替代最终检查。

性能变化按[共同规则](prototype-quality.md)冻结同条件输入和目标，使用生产构建测量，默认五次中位数与独立复测。

## 六、最后怎么验收

改后版本必须同时通过：

### 工程检查

- lint、类型、现有状态测试、生产构建和交付验证通过。
- 构建产物来自最新源码，没有缓存或旧版本污染。

### 页面内容与样式

- 页面内容逐项一致。
- 在固定环境、视口、数据和状态下比较截图与浏览器计算后的关键样式 `computed style`。
- 稳定区域默认零差异；抗锯齿等噪声必须有定位证据，不能自动接受。

### 操作与状态

- 关键入口、动作、禁用、失败、重复执行、刷新、返回和恢复结果一致。
- 路由、稳定 ID、本地存储结构、冻结快照、一次性限制和旧数据恢复一致。
- 控制台没有新增相关错误或警告。

### 交付检查

- 交付形态、目标、路由、资源内联和外链约束保持一致。
- 改前文件和源码未被改后版本的构建或交付脚本覆盖。

### 代码确实得到改善

- 至少一项开工前约定的内部指标得到实证改善。
- 如果外部结果不变但内部指标没有改善，只能说明“代码发生变化”，不能宣布优化完成。

## 七、交付与说明

保留可恢复的改前版本，沿用项目 Git 主线和恢复方式；无版本管理时才建立独立副本。最终检查通过前不覆盖现有正式交付物；需要覆盖时先验证临时产物，再原子替换并写后回读。不要生成散乱备份文件。

默认只完成本地交付。发布、回推、部署或对外发送仍需单独授权。

最终回复说明：

- 改前版本与改后版本的位置、版本和哈希。
- 必须保持不变的内容与实际检查范围。
- 内部修改边界和优化指标的前后结果。
- 工程、页面内容、样式、操作、状态和交付检查结果。
- 已声明的噪声、例外、未覆盖项和回退状态。
- 改前版本是否保持未修改，以及是否执行远端发布。
